## What standard should an aula certificate target in 2026

### 1. W3C Verifiable Credentials — current status

The **VC Data Model v2.0** reached **W3C Recommendation on 15 May 2025** (https://www.w3.org/TR/vc-data-model-2.0/). Two companion specs reached Recommendation the same day:

- **VC Data Integrity 1.0** (https://www.w3.org/TR/vc-data-integrity/) — the "embedded proof" securing mechanism (JSON-LD + a `proof` block). It doesn't define cryptosuites itself; those live in separate specs: EdDSA Cryptosuites (`eddsa-rdfc-2022`), ECDSA Cryptosuites (`ecdsa-rdfc-2019`), BBS Cryptosuites (selective disclosure).
- **Securing Verifiable Credentials using JOSE and COSE** (https://www.w3.org/TR/vc-jose-cose/) — the "enveloping proof" mechanism: wrap the credential as a JWT (JOSE) or CBOR (COSE), reusing existing signing infrastructure.

The spec text is explicit that a conformant document "MUST be secured by at least one securing mechanism," but leaves which one open. That optionality is not academic — the two mechanisms serve different ecosystems in practice, per what I found:

- **Data Integrity / `eddsa-rdfc-2022`** is what the education-credential world (1EdTech, DCC) actually implements — see §4.
- **JOSE/JWT** is what the mobile-wallet/mDL/OpenID4VC world (EU Digital Identity Wallet, ISO 18013-5 interop) uses, per the `openid/dchp` working group harmonizing ISO mDL with OpenID4VP (found via GitHub search).

So "pick JOSE or Data Integrity" is really "pick which ecosystem you're targeting," and they don't fully interoperate today.

Minimal issuer conformance (from the spec text): required properties (`@context`, `type`, `issuer`, `credentialSubject`), a securing mechanism applied, output as `application/vc`. That's a low bar on paper. What's not low: there is no W3C-conformant "issuer API" — VC-API (the HTTP interface DCC's tooling implements) is still a W3C CCG (Community Group) work item, not a Recommendation. So "implement W3C VC" gives you a document format and a signature format, not a deployable issuance/verification protocol — you'd still be designing the API surface yourself, same as today.

**Revocation is explicitly out of scope of the core spec.** VC Data Model v2.0 defines a `status` property as an extension point and defers the mechanism entirely (https://www.w3.org/TR/vc-data-model-2.0/).

### 2. Open Badges 3.0 / CLR — is it the relevant profile, and what does certification cost

Yes — Open Badges 3.0 (1EdTech, aligned to VC 2.0, https://www.imsglobal.org/spec/ob/v3p0) is exactly the profile for "person completed course X, N hours, dates, grade": it defines `OpenBadgeCredential` with an `achievement` claim, plus `ClrCredential` (Comprehensive Learner Record) for a fuller transcript and `EndorsementCredential` for third-party endorsement. This is the right vocabulary if you were going to do VC at all.

**Certification is not free or open.** Per the spec's own cert page (https://www.imsglobal.org/spec/ob/v3p0/cert, confirmed via Context7 and WebFetch): "You must be an 1EdTech Digital Credentials and Badges Alliance Member, an 1EdTech Affiliate Member, or 1EdTech Contributing Member." I could not find published dollar figures on either the membership page (https://www.1edtech.org/about/membership) or the cert page — pricing is by-contact-only, which is itself informative: this is a paid, negotiated, US-based-consortium gate, not a self-serve open standard you implement and are done with.

The minimal conformance bar, though, is genuinely light: "Issuer Only" conformance requires issuing one valid badge to `conformance@imsglobal.org` and demonstrating (by video) how a recipient retrieves it. Full "Host" conformance (Service Consumer/Provider Read+Write, OAuth2 discovery/token/credentials endpoints) is a real integration project — building a mini OAuth2 resource server just to hand a JSON document to whichever badge-wallet product asks for it.

Real commercial adoption of the certification exists: 1EdTech's public search results show Badgr/Canvas Credentials, Credly, Accredible, and POK carrying OB3.0 issuer certification in 2025–2026, plus smaller players (Badge Engine, certified 2026-07-01). That's evidence the certification pipeline is live and used by ed-tech vendors selling *to* institutions — not evidence that institutions like CICAT gain anything by certifying themselves, since the value of certification is chiefly "our badges display correctly inside Credly/Badgr/LinkedIn," and CICAT isn't targeting badge-wall products.

### 3. Revocation: what the specs actually require

- VC Data Model: optional `credentialStatus` extension point, no mandated mechanism (§1 above).
- **Bitstring Status List v1.0** reached **W3C Recommendation 15 May 2025** (https://www.w3.org/TR/vc-bitstring-status-list/), superseding the earlier "StatusList2021" that DCC's tooling still names in its repos (`credential-status-manager-git`, `status-service-db`). Mechanism: issuer publishes a signed `BitstringStatusListCredential` — a GZIP-compressed bitstring, **minimum 16KB uncompressed (131,072 bits)**, explicitly sized that large for k-anonymity so that revoking one credential doesn't reveal which one via list-size correlation. Each credential carries an index into this list. A verifier must fetch the list, verify its own signature, and check the bit.
- 1EdTech's OB3.0/CLR implementation guide (https://www.imsglobal.org/spec/ob/v3p0/impl, via Context7) confirms this is **optional**, not required for OB3.0 conformance: "OB and CLR reference optional 1EdTech extensions supporting verifiers in obtaining updated representations of credentials and checking for revocation... issuers often need to produce the credential without knowing which other parties might someday rely on it or what methods those verifiers may support." A certified OB3.0 issuer can ship with zero revocation support and still pass certification.

This 16KB-minimum, privacy-preserving batch design solves a specific problem: letting a verifier check revocation *without revealing to the issuer which credential is being checked, or to an eavesdropper which one was flagged*. That's the right tool when a credential circulates in wallets outside the issuer's control and the issuer would otherwise learn "someone is checking student #4419 right now." It is solving a problem aula does not have — every verification of a CICAT certificate already hits CICAT's own `/verificar/<code>` endpoint, so CICAT already knows which certificate was checked, by design, on every verification event that exists today.

### 4. Who actually ships this, and does it reach Peru

**Digital Credentials Consortium (DCC)** — MIT-led, ~20 North American universities, is the strongest real running implementation I found (https://dcconsortium.org/, GitHub org `digitalcredentials` — confirmed live: 30+ repos, commits as recent as this week). It implements exactly the "modern" stack: VC-API issuance (`issuer-coordinator`, `sign-and-verify`), Data Integrity proofs (`eddsa-rdfc-2022`), BitstringStatusList/StatusList2021 (`status-service-db`), a mobile holder wallet (`learner-credential-wallet`), and a public verifier (`verifier-plus`). Critically, DCC also maintains `dcc-known-registries` and `dcc-pilot-registry` — **a curated list of DIDs the wallet/verifier trusts**. This means DCC's "open standard" verification still resolves to a closed trust list; a random employer's off-the-shelf verifier does not automatically trust a CICAT-issued VC any more than it would trust a CICAT PDF — it would need CICAT's DID added to a registry it consults, which is a bootstrapping problem, not a technology problem, and identical in kind to "the employer needs to know to trust cicat.edu.pe."

**EU Europass Digital Credentials / EBSI** — the strongest government-backed effort. But per the European Commission's own EBSI pages (via WebSearch), **EBSI's business launch to production is planned for Q4 2026** — as of today (2026-09-11) the EU's flagship sovereign VC infrastructure is still pre-production. Existing "success stories" cited (Montpellier Business School since 2021, University of Monterrey) are vendor deployments — specifically BCdiploma, a commercial blockchain-notarization vendor — not open OB3.0/W3C-VC interop; verification in these case studies still resolves to visiting a vendor-hosted URL, functionally the same UX as aula's `/verificar/<code>` today, just with a proprietary format underneath.

**Peru specifically**: SUNEDU (the Peruvian higher-education regulator) already runs the pattern aula is proposing, at national scale, today: a government registry (`Registro Nacional de Grados y Títulos`) with a public online lookup — by DNI or QR — with no VC, no wallet, no DID (https://www.sunedu.gob.pe/registro-nacional-de-grados-y-titulos/, https://constancias.sunedu.gob.pe/). This is the de facto national precedent every Peruvian employer, university admissions office, and notary already knows how to use. There is no evidence in any of the above that Peruvian employers, SUNEDU, or MINEDU consume OB3.0 or W3C VC, and general adoption research (Gartner's 2023 "early mainstream," 5–20% penetration figure, cited via WebSearch summary of idura.eu/dock.io analyses) describes a chicken-and-egg problem between issuers and verifiers that is unresolved industry-wide, let alone in Peru.

### 5. The null hypothesis: signed PDF + DB verification page

**PAdES** (ETSI EN 319 142, current parts at v1.2.1 2024/2025, https://www.etsi.org/deliver/etsi_en/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf) builds on ISO 32000 PDF signatures and defines four baseline levels — B-B, B-T, B-LT, **B-LTA**. B-LTA embeds the certificate chain, revocation evidence, and a trusted timestamp *inside the PDF itself*, so the signature can be validated years later even after the signing cert or CA has expired or the issuer's servers are gone (https://en.wikipedia.org/wiki/PAdES; encryptionconsulting.com summary via WebSearch). This is a mature, ISO/ETSI standard with **no membership fee and no certification gate** — any qualified/ordinary signing certificate and a standard PDF library implement it.

What this combination (typst-produced PDF, ideally PAdES-signed, plus a DB-backed `/verificar/<code>`) already covers for aula's stated requirements:
- Tamper evidence: the DB record is authoritative regardless of what the PDF says, and a PAdES signature additionally proves the *PDF bytes* weren't altered after generation — useful because the print-then-release workflow means a physical, hand-signed document exists before the DB record is "released."
- Revocation: a boolean/status column, checked on every request. No 16KB minimum, no batch-privacy design, no separate publish step — because there's no third party you're hiding the check from.
- Print-first-then-release: trivially a status flip in the DB; a VC/OB3.0 flow instead has to solve "allocate a credential now, but don't make it independently verifiable/portable until later," which the spec doesn't have a first-class mechanism for.

Where it stops covering things: a signed-PDF-plus-URL certificate has zero portability into a third-party wallet, cannot be selectively disclosed, and doesn't let an *offline* verifier (no network) check revocation status against anything but the PDF's own signature — but neither does aula's stated model require any of that.

## Recommendation for aula

**Do not adopt W3C Verifiable Credentials or Open Badges 3.0 for aula's certificates in 2026. Keep the signed-PDF-plus-`/verificar/<code>`-page model, and add a PAdES B-LTA signature on the generated PDF as the one concrete upgrade.**

Why the evidence supports this: every verifier CICAT's graduates actually face — Peruvian employers, other Peruvian institutes, SUNEDU-adjacent processes — already operates on exactly the pattern aula uses today, because SUNEDU itself runs the national credential registry that way (§4). No evidence surfaced of a Peruvian consumer of OB3.0/VC. The two international ecosystems that do exist (DCC, EBSI/Europass) either gate trust through their own closed registries (DCC) or aren't in production yet (EBSI, Q4 2026 target) — so certifying against the standard buys interoperability with an ecosystem that, as of today, doesn't include any of CICAT's actual verifiers. OB3.0 certification additionally requires paid 1EdTech membership with no published price (§2), for a "minimal" conformance bar that's cheap to pass but has no local consumer, and a "full" conformance bar (OAuth2 issuance API, wallet interop) that's a genuine engineering project. Revocation via BitstringStatusList (§3) solves an anonymity problem — hiding which credential is being checked from the issuer — that doesn't exist in aula's model, since the verifier always visits CICAT's own endpoint anyway; a DB status column is strictly simpler and sufficient.

What it costs: if a future funder, an international employer, or a Peruvian regulatory modernization (MINEDU/SUNEDU moving to VC, or an EU-funded health-training partnership requiring Europass-recognized credentials) requires portable/cryptographic credentials, aula will need to add an export path later. That's a real but bounded cost, not a foreclosed one — the domain model behind a certificate (person, course, hours, dates, grade) maps directly onto `credentialSubject`/`achievement` in OB3.0 if that day comes, so nothing in the current design needs to be re-architected to add a VC/OB3.0 export alongside the existing PDF later. The case against this recommendation is real: it's a bet that the standard stays irrelevant to CICAT's actual verifiers through the certificate's practical lifetime, and the international pull (EBSI, DCC, 1EdTech-certified commercial LMS vendors) is genuine momentum that could eventually reach Peru faster than expected — but "could eventually" is not evidence of a verifier that exists today, and building for it now is ceremony this specific institute doesn't need yet.
