# picv-2025 and rqueue defects

Defects found in picv-2025 and in the rqueue library it depends on, each one
reproduced during a gate round and left alone deliberately so it would not
widen the task that found it. They are real and unfixed. Read this before
opening a task in either.

- 2026-09-05 - picv-2025/rqueue: build a real Procrastinate-to-rqueue data migration command for compute.procrastinate_jobs (move rows from the old queue table to task_queue.jobs before cutover). No live deployment needs it today (confirmed across 3 gate rounds on cap/picv-asyncpg-rqueue-v2), but it's real user-facing value for whenever a real deployment does cut over -- don't build it speculatively now, but worth a real stage-2/3 task when that need is closer.
- 2026-09-05 - rqueue: Worker.run() doesn't actually return promptly on shutdown when a handler used asyncio.to_thread for long CPU-bound work. bounded_default_executor's cleanup (executor.py) calls ThreadPoolExecutor.shutdown(wait=True) synchronously on the event loop when the Worker's _runtime() context manager exits -- this blocks until every submitted thread genuinely finishes, even though _shutdown_inflight() already cancelled the coroutine and handed the lease back within shutdown_timeout. Confirmed directly: a 3s blocking thread, cancelled at ~0.1s, still blocks the 'with bounded_default_executor(...)' block's exit for the full 3s. For a tens-of-minutes handler this means the worker process doesn't actually exit on SIGTERM until the in-flight work finishes on its own, even though the lease was already correctly handed back to another worker -- two workers can then be alive concurrently past the point rqueue's own shutdown sequence implies is safe. Likely fix: shut the executor down off the loop thread (asyncio.to_thread(executor.shutdown, wait=True)) or with wait=False plus a documented note that threads may outlive the executor. Found via picv-2025's cap/picv-asyncpg-rqueue-v2 gate review (round 5); out of scope for that task since the defect is in rqueue itself.
- 2026-09-06 - rqueue.roles: Capability.CONSUME's _TABLE_GRANTS includes INSERT on jobs (SELECT, INSERT, UPDATE), letting a compromised consumer enqueue arbitrary tasks despite the capability being named/documented as consume-only. Found reviewing picv-2025's queue role provisioning (picv-rqueue-operability-v2).
- 2026-09-06 - rqueue.roles.provision_role: re-running against an existing role only does ALTER ROLE ... LOGIN [PASSWORD ...] plus schema/table REVOKEs; it never strips SUPERUSER/CREATEROLE/CREATEDB/BYPASSRLS or role memberships, so a role that drifted to elevated privileges (e.g. manual grant, name collision) is not demoted on re-provisioning despite the docstring's 'repairs a role that has drifted' claim. Found reviewing picv-2025's queue role provisioning (picv-rqueue-operability-v2).
