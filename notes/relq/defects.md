# relq defects

Defects found in relq while Captain was working on something else, each one
reproduced and left alone deliberately so it would not widen the task that
found it. They are real and unfixed. Read this before opening a task in relq.

- 2026-09-04 - relq: any Column-typed parameter (on_conflict, from_select, excluded/returning) can be handed an adversarial subclass that overrides __init__ to skip NodeValue's construction-token seal (e.g. class Sneaky(Column[str]): def __init__(self): pass). This type-checks under basedpyright strict (no diagnostic exists for an incompatible __init__ override) but raises a raw AttributeError: '...' object has no attribute '_state' deep inside compilation instead of a clean validation error. Confirmed pre-existing on from_select's original, untouched Column[A] overload ladder (not introduced by relq-conflict-where/relq-conflict-arity). Fix would mean changing relq's runtime validation repo-wide to check the compiled AST node type instead of nominal isinstance(x, Column), which is a real, separate task. See notes/relq/relq-conflict-where.md, 'The wall' and 'The finding that decides it' sections, for the full investigation.
- 2026-09-05 - relq: Column's dataclass-generated frozen __setattr__/__delattr__ raises a raw TypeError ('super(type, obj): obj (instance of Column) is not an instance or subtype of type (Column)') instead of dataclasses.FrozenInstanceError whenever code attempts to mutate a Column instance's attribute (e.g. users.id.foo = 1). Confirmed pre-existing: reproduces identically on cap/relq-conflict-arity (before any Python-floor work) under Python 3.15.0rc1, so it is unconditional and version-independent, not tied to the 3.13/3.14 patch-release bisection found while lowering the floor. Root cause: dataclasses' own generated frozen accessor methods close over the pre-slots-rebuild class object via the same super(cls, self) pattern that _node_value.py's NodeValue fix addresses for hand-written methods, but Column (and potentially other @dataclass(frozen=True, slots=True) classes elsewhere in relq, e.g. query.py's SelectQuery family) still ask for slots=True via the decorator and were never audited. A caller catching AttributeError/FrozenInstanceError to detect a mutation attempt gets an uncaught TypeError instead. Fix would mean applying the same hand-declared-__slots__-instead-of-slots=True treatment (and getstate/setstate correctness) across every frozen+slotted dataclass in relq, verified the same way NodeValue was - real, separate task, not part of lowering the Python floor. See notes/relq/relq-conflict-where.md for the floor task's own investigation.
- 2026-09-09 - relq: Expr.nullable() only clears the outer-join nullability check when applied to the outermost node. x.nullable().as_('a') is rejected; x.as_('a').nullable() is accepted for the same query and types. _validate_selection_nullability early-returns on a top-level NullableResultNode, but _nullable_result_sources recurses straight through it under an AliasNode. Pre-existing on master, reproduced with a plain Column, unrelated to any in-flight task. Needs a design decision before fixing: whether a marked subexpression should also clear the requirement for enclosing arithmetic (e.g. add(a.x.nullable(), b.y)) depends on whether add propagates optionality in its overloads. Found by relq-foundation-query-shapes' gate round 6; left alone there deliberately to avoid scope creep on an already-converging task.
