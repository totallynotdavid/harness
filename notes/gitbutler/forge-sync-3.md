GitButler syncs a rewritten stack in two phases: push the refs, then update the existing PR records.

1. Force safety is conditional. The workspace push passes `with_force` and the project’s protection setting to the lower layer (`crates/but-workspace/src/legacy/push.rs:116-128`). That layer constructs `git push --quiet --no-verify <remote> <refspec>`; force protection adds `--force-with-lease` and, for non-deletions, `--force-if-includes`; otherwise it adds plain `--force` (`crates/gitbutler-git/src/repository.rs:526-545`). The unqualified lease uses Git’s remote-tracking ref as the expected value. `remote_before_sha` is only recorded in the result, not passed as an explicit `=<sha>` lease (`crates/but-workspace/src/legacy/push.rs:86-87,137-141; crates/gitbutler-git/src/repository.rs:255-264`). Replicate the safe case with `git push --force-with-lease --force-if-includes origin B2:B2` (and similarly for B1/B3).

2. It does not close or reopen PRs. After all ref pushes, the API invokes review synchronization (`crates/but-api/src/legacy/workspace.rs:421-434`). GitHub updates an existing `/pulls/{number}` resource with PATCH (`crates/but-github/src/client.rs:1126-1167`); the sync passes `state: None` (`crates/but-forge/src/review.rs:2939-2952`). Pushing the same head branch therefore leaves the PR—and its review threads/comments—intact; there is no create/delete step in this path.

3. Yes, base changes are explicit. GitButler computes bottom-to-top targets (`crates/but-forge/src/review.rs:3331-3355`) and PATCHes each GitHub PR’s `base` (`crates/but-forge/src/review.rs:3015-3035`). Native GitHub stacks are dissolved before conflicting retargets and recreated afterward (`crates/but-forge/src/review.rs:3004-3047`; `crates/but-github/src/stacks.rs:173-215`). It does not depend on branch deletion behavior. Unchanged native members are locked and skip redundant base PATCHes (`crates/but-forge/src/review.rs:3020-3023`).

4. Ordering is explicit: the selected scope is top-to-base, but refs are pushed in reverse, bottom-to-top (`crates/but-workspace/src/legacy/push.rs:60,147-177`; test evidence: `crates/but-workspace/tests/workspace/push.rs:288-310`). PR synchronization happens only after ref pushing (`crates/but-api/src/legacy/workspace.rs:421-434`), then updates are issued sequentially in bottom-to-top order (`crates/but-api/src/legacy/forge.rs:1934-1964`).

5. Unexpected remote movement is prevented only when protection is enabled: the lease/inclusion flags make Git reject the overwrite, classified as `ForcePushProtection` (`crates/gitbutler-git/src/repository.rs:567-568`). With protection skipped, it is an unsafe plain `--force`; there is no separate but-forge/GitHub preflight CAS.
