# Graph-rebase findings

1. **Propagation.** `but_graph::Graph` preserves the commit graph; the workspace is only a presentation projection (`crates/but-graph/src/lib.rs:24-41,104-122`). `Editor::create()` turns every traversed commit into a `Pick`, refs into `Reference` steps, and marks only segments reachable from mutable entrypoints (normally `HEAD`) as rewriteable (`crates/but-rebase/src/graph_rebase/creation.rs:56-99,119-187`).

An amend creates a new commit, then `replace()` swaps the old pick and records old-to-new history (`crates/but-workspace/src/commit/commit_amend.rs:62-114`; `crates/but-rebase/src/graph_rebase/mutate.rs:336-352`). Insertion instead rewires the selected node's child or parent edges (`crates/but-rebase/src/graph_rebase/mutate.rs:768-817`). `Editor::rebase()` topologically orders the graph parent-first (the stored edges point child-to-parent, so it reverses petgraph's order), then for each mutable pick looks up its original parents' already-produced IDs and cherry-picks onto those IDs (`crates/but-rebase/src/graph_rebase/rebase.rs:21-109,223-231`). It reconnects all edges to the corresponding output nodes (`crates/but-rebase/src/graph_rebase/rebase.rs:174-187`). Thus a changed deep commit causes only affected descendants to get new IDs; sibling branches whose parents did not change can remain verbatim. The replace test shows A changing while B remains, but the merge and top are recreated (`crates/but-rebase/tests/rebase/graph_rebase/replace.rs:176-227`). Reference steps map their first parent to the new ID and produce precise update edits; leftover mutable refs are deleted (`crates/but-rebase/src/graph_rebase/rebase.rs:111-205`).

`materialize()` persists the in-memory objects, performs checkout handling, submits the accumulated ref edits in one `repo.edit_references()` call, and refreshes the workspace (`crates/but-rebase/src/graph_rebase/materialize.rs:197-299`).

2. **Compared with cascaded `git rebase --onto`.** For one linear branch with one tip ref, the result is essentially the same. The command alone does not, however:

* move refs located inside the selected range; the editor models each ref at its exact graph position and updates it (`crates/but-rebase/src/graph_rebase/creation.rs:124-171`; `crates/but-rebase/src/graph_rebase/rebase.rs:111-164`);
* preserve merge topology: plain `--onto` flattens merges, while the editor retains ordered multiple parents and merges old bases with new onto parents (`crates/but-graph/src/lib.rs:389-411`; `crates/but-rebase/src/graph_rebase/cherry_pick.rs:64-85,104-218`);
* express graph-wide insertion/reordering while sharing nodes between branches; it would need separate, carefully coordinated commands (`crates/but-rebase/src/graph_rebase/mutate.rs:604-725,768-817`);
* provide GitButler's cross-branch conflict policy. The editor can create a conflicted commit and continue above it, or reject it when `conflictable` is false; independent `--onto` runs stop in separate conflict states (`crates/but-rebase/src/graph_rebase/rebase.rs:62-107`; `crates/but-rebase/src/graph_rebase/cherry_pick.rs:14-35`).

3. **Legacy engine.** Yes, conceptually for a simple line: it starts a cursor at `base` and sequentially cherry-picks ordered steps (`crates/but-rebase/src/lib.rs:221-311`). But it is one caller-supplied linear sequence, not a descendant-branch discovery/cascade; it explicitly warns that all inputs become sequential (`crates/but-rebase/src/lib.rs:112-143`). It emits ref locations for the caller rather than updating refs itself (`crates/but-rebase/src/lib.rs:131-143,414-438`) and has special merge/squash handling (`crates/but-rebase/src/lib.rs:245-345`).

4. **Conflicts and atomicity.** Tree conflicts are returned as `ConflictedCommit` (with conflict metadata), while failure to merge original or new parent bases is an error; `conflictable = false` turns a resulting conflict into a rebase error (`crates/but-rebase/src/graph_rebase/cherry_pick.rs:146-218`; `crates/but-rebase/src/graph_rebase/rebase.rs:71-107`). Checkout conflicts are separately reported as `checkout_conflict_occurred` (`crates/but-rebase/src/graph_rebase/materialize.rs:237-253`; `crates/but-rebase/src/graph_rebase/mod.rs:530-533`). The history replay is one graph-wide in-memory pass, with no per-branch checkpoints; refs are committed together in one transaction call after checkout work, not branch-by-branch (`crates/but-rebase/src/graph_rebase/materialize.rs:218-290`).
