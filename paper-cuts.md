# Paper cuts

Friction in Captain itself: harness quirks, broken scripts, and skills that misfire.

Generated by `cap papercut` from `paper-cuts.jsonl`. Log with
`cap papercut add <subject> "<text>"`; remove fixed entries with
`cap papercut close <id>`.

A defect in a project Captain was working on is not a paper cut. It goes in
`notes/<project>/defects.md`, where the next task on that project will find it,
and `cap papercut` refuses a project as a subject.

A defect belongs here only while it is open.

- [ ] #24 2026-09-10 `unsorted` - `pgrep -f` is unusable for polling task processes once `cap send` has revived a session, because the revive puts the captain's entire message inside the launch prompt and the harness carries that prompt in its argv. A gate round's instructions run to several thousand characters and quote the exact commands the agent is told to run, so `pgrep -f 'mise run check'` matched the claude session itself, not the check. Hit twice in a row today on local-env: two `until ! pgrep -f ...; do sleep; done` waiters never terminated because the agent's own command line kept matching, and one had to be killed by hand. Anything that waits on a task's real work should watch the work's own output file or pid, or at least anchor the pattern to the binary (`pgrep -f '^mise '`, `pgrep -x`), never a phrase that could appear in a brief or a captain message. Worth considering whether cap-send should pass the revival text through a file or stdin instead of argv, since argv is world-readable on this box and the same message can carry findings that quote source.
- [ ] #25 2026-09-10 `unsorted` - killing cap-gate does not kill the review it launched, so the account keeps paying for an Opus session whose verdict nobody will ever record. herdr starts the reviewer in its own pane, detached from cap-gate's process tree, so when the harness's low-memory guard killed the backgrounded `cap gate local-env --full` seconds after it started, the wrapper died and the opus process (pid 1637014, pane w2:p1E) carried on reviewing for another ten minutes with nothing left to read its output, promote the report or call gate_record. Recovered by hand this time: waited on the orphan's pid, read the pane, wrote notes/classroom/local-env.gate-A.md and called gate_record with the fingerprint directly. The same shape applies to any interruption of cap-gate, Ctrl-C included, and it is worse than a wasted review because state/tasks/<slug>/gate.json still holds the previous round's verdict at a stale fingerprint, which reads exactly like a gate that was never run. cap-gate should either trap EXIT and close the pane it opened, or record enough (pane id, fingerprint, profile) that a later run can adopt an orphaned review instead of paying for it twice. Followed up 2026-09-10, fourteen hours later: pid 1637014 was still resident and idle, holding 211MB, long after its task record had been dropped and its findings had been recovered by hand into notes/classroom/defects.md. Killing it returned about 900MB. So the cost is not only the wasted review, it is a process that never exits and that nothing in Captain knows about, on a box whose low-memory guard then starts killing live work instead: it reaped three of the captain's own background waiters while the orphan it could not see kept its memory. Whatever cap-gate records about a review it launches has to include the pid, so a later run can reap it as well as adopt it.
- [ ] #37 2026-09-10 `unsorted` - Piping `cap verify` into anything hangs forever after the run finishes, because the checks start detached containers that inherit the pipe. `cap verify --repo classroom | tail -30` sat with a live `tail` and no writer for twelve minutes; the process tree showed `bash---tail` and nothing else, so `cap verify` had already exited. podman's conmon, php-fpm and the cron loop all keep the inherited write end of that pipe open after `compose up -d` returns, so `tail` never sees EOF and never prints the buffered output. Killing it destroyed a seven-minute run's entire output, and the run had genuinely failed (port 8080 was held by another worktree's stack), so the reason was lost with it. Redirecting to a file instead of piping avoids it completely. Worth deciding whether cap-verify should write its own log and print a summary so a caller never reaches for a pipe, or whether the devstack tasks should start containers with their fds closed. The general shape applies to any cap command that brings a container stack up, not just verify.
- [ ] #50 2026-09-11 `unsorted` - `cap commit` wrote a body that restated the diff for all five commits it produced this session, and split one logical change into two commits whose halves cannot stand alone (a compose file and the document explaining it). rules/commits.md says the body must state why, not what, and `cap land` does not check bodies, only the summary line, so nothing catches it. Every message had to be rewritten by hand before landing. Related to the entry above on `cap commit` not enforcing the rules `cap land` refuses on; this is the same gap measured at 5 of 5.
- [ ] #56 2026-09-13 `unsorted` - `cap gate`, `cap commit`, and `cap check` give the captain session no way to notice completion other than blocking on them or hand-rolling a poll loop, because they are foreground CLI commands with no herdr pane and no state-file signal the reminder hook reads. A crew pane's stop already surfaces automatically as "has stopped and is waiting on you", but a `cap gate --full` run started in the background has nothing equivalent: the captain caught a session writing its own `until kill -0 $pid` watcher twice in one sitting and said the harness should raise this, not the session. The fix is the same reminder-hook mechanism crew panes use, extended to these dispatch commands, not another watcher pattern to remember to reach for. Not fixed now: surfaced while `pipeline-hardening`, the task that owns `bin/cap-gate`/`bin/lib.sh`, was mid-review.
