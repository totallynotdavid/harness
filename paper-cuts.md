- [ ] 2026-09-05 - relq: Column's dataclass-generated frozen __setattr__/__delattr__ raises a raw TypeError ('super(type, obj): obj (instance of Column) is not an instance or subtype of type (Column)') instead of dataclasses.FrozenInstanceError whenever code attempts to mutate a Column instance's attribute (e.g. users.id.foo = 1). Confirmed pre-existing: reproduces identically on cap/relq-conflict-arity (before any Python-floor work) under Python 3.15.0rc1, so it is unconditional and version-independent, not tied to the 3.13/3.14 patch-release bisection found while lowering the floor. Root cause: dataclasses' own generated frozen accessor methods close over the pre-slots-rebuild class object via the same super(cls, self) pattern that _node_value.py's NodeValue fix addresses for hand-written methods, but Column (and potentially other @dataclass(frozen=True, slots=True) classes elsewhere in relq, e.g. query.py's SelectQuery family) still ask for slots=True via the decorator and were never audited. A caller catching AttributeError/FrozenInstanceError to detect a mutation attempt gets an uncaught TypeError instead. Fix would mean applying the same hand-declared-__slots__-instead-of-slots=True treatment (and getstate/setstate correctness) across every frozen+slotted dataclass in relq, verified the same way NodeValue was - real, separate task, not part of lowering the Python floor. See notes/relq/relq-conflict-where.md for the floor task's own investigation.

- [ ] 2026-09-05 - rqueue: Worker.run() doesn't actually return promptly on shutdown when a handler used asyncio.to_thread for long CPU-bound work. bounded_default_executor's cleanup (executor.py) calls ThreadPoolExecutor.shutdown(wait=True) synchronously on the event loop when the Worker's _runtime() context manager exits -- this blocks until every submitted thread genuinely finishes, even though _shutdown_inflight() already cancelled the coroutine and handed the lease back within shutdown_timeout. Confirmed directly: a 3s blocking thread, cancelled at ~0.1s, still blocks the 'with bounded_default_executor(...)' block's exit for the full 3s. For a tens-of-minutes handler this means the worker process doesn't actually exit on SIGTERM until the in-flight work finishes on its own, even though the lease was already correctly handed back to another worker -- two workers can then be alive concurrently past the point rqueue's own shutdown sequence implies is safe. Likely fix: shut the executor down off the loop thread (asyncio.to_thread(executor.shutdown, wait=True)) or with wait=False plus a documented note that threads may outlive the executor. Found via picv-2025's cap/picv-asyncpg-rqueue-v2 gate review (round 5); out of scope for that task since the defect is in rqueue itself.

- [ ] 2026-09-09 - `[ cond ] && cmd` as a bare statement (not an if/while condition, no trailing `|| true`) silently aborts the whole script under captain's `set -e` whenever cond is false, because the bare list's own exit status is the test's false result. Hit twice for real today: bin/cap-ask's last line (`[ -n "$resume_file" ] && rm -f ...`) made cap-ask exit 1 after every successful non-claude call, discarding Gate B's verdict inside cap-gate's pipefail (fixed, see git log); the fix I first wrote for pane_send's chunking loop (`[ "$i" -lt "$n" ] && sleep 0.15`) reproduced the identical failure immediately (also fixed, both now use `if`). `grep -rn '^\s*\[ .* \] &&' bin/ | grep -v '||'` turns up 50+ more matches across cap-skills, cap-gate, cap-spawn, cap-reconcile, cap-drop, cap-land, cap-verify, cap-restack, cap-explore, cap-watch, cap-check, cap-map, cap-crew, cap-conventions, and lib.sh itself - most are probably fine (if/while conditions are exempt, some already have a following command that masks it), but nobody has actually gone through and confirmed which. Needs a real audit, one at a time, checking whether each is actually reachable with a false condition and whether that's the last command in its context - not a blind find-and-replace to `if`, since some of these are deliberately using the short-circuit for a real conditional side effect and blindly converting could change behavior in a way that's harder to spot than the current bug.
- [ ] 2026-09-09 - relq: Expr.nullable() only clears the outer-join nullability check when applied to the outermost node. x.nullable().as_('a') is rejected; x.as_('a').nullable() is accepted for the same query and types. _validate_selection_nullability early-returns on a top-level NullableResultNode, but _nullable_result_sources recurses straight through it under an AliasNode. Found by relq-foundation-query-shapes' gate round 6; left alone there deliberately to avoid scope creep on an already-converging task.

- [x] 2026-09-09 - cap gate has no lock, so two runs on the same task race. Found live on local-env: PIDs 296983 and 306107 were both running 'cap-gate local-env --full' at 11:12, each with its own Gate A opus session, both tee-ing to the same notes/classroom/local-env.gate-A.md and both about to write the same state/tasks/local-env/gate.json. - [x] 2026-09-09 - cap-ask's resume key could not tell one gate round from the next, so a gate resumed a finished review and restated its verdict against code it had never read. The key is sha256(profile, dir, prompt), and cap-gate sends a byte-identical review prompt every round from the same worktree with the same profile. local-env's Gate A hit its session limit at 11:51 after reaching GATE: FAIL on a missing executable bit; the round-five gate at 16:16 resumed that session, got its old conclusion restated verbatim (the capture still carried the 11:51 timestamp), and recorded FAIL against a fingerprint whose worktree had the bit set. The report file came back byte-identical to the committed one, which is what gave it away. Gate B, which had no pending resume, genuinely re-ran and passed. Fixed 2026-09-09: cap-ask folds an optional CAP_ASK_KEY into the resume key and cap-gate passes the worktree fingerprint, so a resume can only ever continue a review of the exact code that was interrupted. Any other caller whose prompt is constant across calls that mean different things must supply its own discriminator.
