# Paper cuts

Friction in Captain itself: harness quirks, broken scripts, and skills that misfire.

A defect in a project Captain was working on is not a paper cut. It goes in
`notes/<project>/defects.md`, where the next task on that project will find it.
The ledger drifted from this once and carried seven relq and rqueue bugs that no
Captain change could ever close.

Closed entries stay. The "Fixed:" paragraphs are the only written record of why
several of these scripts are shaped the way they are, and other files cite them.

- [x] 2026-09-09 - `[ cond ] && cmd` as a bare statement (not an if/while condition, no trailing `|| true`) silently aborts the whole script under captain's `set -e` whenever cond is false, because the bare list's own exit status is the test's false result. Hit twice for real today: bin/cap-ask's last line (`[ -n "$resume_file" ] && rm -f ...`) made cap-ask exit 1 after every successful non-claude call, discarding Gate B's verdict inside cap-gate's pipefail (fixed, see git log); the fix I first wrote for pane_send's chunking loop (`[ "$i" -lt "$n" ] && sleep 0.15`) reproduced the identical failure immediately (also fixed, both now use `if`). `grep -rn '^\s*\[ .* \] &&' bin/ | grep -v '||'` turns up 50+ more matches across cap-skills, cap-gate, cap-spawn, cap-reconcile, cap-drop, cap-land, cap-verify, cap-restack, cap-explore, cap-watch, cap-check, cap-map, cap-crew, cap-conventions, and lib.sh itself - most are probably fine (if/while conditions are exempt, some already have a following command that masks it), but nobody has actually gone through and confirmed which. Needs a real audit, one at a time, checking whether each is actually reachable with a false condition and whether that's the last command in its context - not a blind find-and-replace to `if`, since some of these are deliberately using the short-circuit for a real conditional side effect and blindly converting could change behavior in a way that's harder to spot than the current bug. Fixed 2026-09-10: the premise was too broad. Bash exempts the test in `a && b` from set -e, so the shape is harmless mid-body; it is only fatal in tail position, where a false test becomes a script's exit status or a function's return value. Of the 68 matches in bin/, two were real: bin/cap-conventions' last line made `cap conventions` exit 1 after successfully writing the file whenever the project had none of AGENTS.md/CLAUDE.md/CONTRIBUTING.md/README.md, and lib.sh's pane_enter, which cap-send calls bare. The other 66 are mid-body, or predicates only ever asked inside a condition, which is the correct way to write that shape. shellcheck reports nothing at any level, so bin/lint-andlist now decides it: a candidate is flagged when every significant line after it out to the end of its function or file is a block closer, and a function tail is only a defect when some call site invokes it bare. It runs as mise's check:andlist, and it reproduces both of the original failures on fixtures.
- [x] 2026-09-09 - cap verify runs only the first matching task when that task reads stdin. Its loop feeds task names in with a here-string, and mise run check (docker compose underneath) consumes the rest, so check:certificate never ran and the command still exited 0. A verification tool silently skipping half its checks is worse than one that fails. Fixed 2026-09-09: cap-verify now iterates an array and runs every check with stdin closed, and reports how many tasks it ran. bin/cap-gate had the identical printf|while shape and would have skipped Gate B once cap-ask consumed the profile list; fixed the same way. - [x] 2026-09-09 - cap gate has no lock, so two runs on the same task race. Found live on local-env: PIDs 296983 and 306107 were both running 'cap-gate local-env --full' at 11:12, each with its own Gate A opus session, both tee-ing to the same notes/classroom/local-env.gate-A.md and both about to write the same state/tasks/local-env/gate.json. Whichever finishes second wins the report, and gate_record's read-modify-write on gate.json can lose the other profile's verdict entirely. It also pays twice for the same review. Fix: take a lock on state/tasks/<slug>/ in cap-gate and refuse a second concurrent run for that slug, the way cap-spawn already refuses a duplicate pane. Fixed 2026-09-09: lib.sh grew task_lock, an flock on state/tasks/<slug>/.lock that cap-gate takes right after task_load, so a second run on the same slug dies naming the pid that holds it. The same round fixed the other half of the damage: cap-gate opened the report with `tee "$out"`, which truncated the last good review before the new session had produced a byte, so a session that died on a quota rejection destroyed it. It now tees to a temp and promotes it only once gate_verdict finds PASS or FAIL. local-env.gate-A.md was found at zero bytes today and restored from git.
- [x] 2026-09-09 - Captain measured no codex quota. Dispatch sizing reads rate-limit windows from what the harness hands its status line (bin/cap-statusline), and that is a Claude Code hook with no codex equivalent, so `usage_read codex` returned unmeasured; cap-ask's session-limit detection was claude-gated too, so a codex rejection blocked nothing. Fixed 2026-09-09: codex writes the same information to disk without being asked. Every turn appends a `token_count` event to its rollout under `~/.codex/sessions/`, carrying `rate_limits` with `primary` (300-minute window) and `secondary` (10080-minute window), each with `used_percent` and `resets_at`, plus a `rate_limit_reached_type` that is non-null once a window is exhausted. Confirmed against a real session on codex-cli 0.153.4 (gpt-5.6-luna at xhigh), which reported primary 4% and secondary 31%. `usage_read codex` now reads the newest rollout and cap-ask blocks a codex profile when `rate_limit_reached_type` is set. The record also carries `plan_type`; Captain deliberately does not read it. Improved 2026-09-09: the rollout is now the fallback, not the source. `codex app-server` answers `account/rateLimits/read` with the windows as they stand right now, which matters because the moment Captain most needs to know whether codex has room is the moment no codex session is running and the newest rollout is hours old. It is one JSON-RPC round trip over stdio, cached for `CAP_USAGE_TTL`, and the reading carries its own source so `cap budget` says which one a number came from.
- [x] 2026-09-09 - `CAP_ASK_PROFILES` is the one setting in config/captain.conf that an environment variable cannot override. Every other value uses `: "${VAR:=default}"`; the profile table is a plain assignment, so `CAP_ASK_PROFILES=... cap models` silently uses the file's table instead. Testing a profile change means editing the file and putting it back. Not urgent, but the header of that file claims all of it can be overridden, and right now that is not true. Fixed 2026-09-10: the table is now `: "${CAP_ASK_PROFILES:=...}"` like every other value, so the file's header is true again. Confirmed with `CAP_ASK_PROFILES='probe claude haiku -' cap models`, which drops every codex profile from the catalog's PROFILE column.

- [x] 2026-09-09 - bash expands every word of a 'local' builtin before it assigns any of them, so 'local slug=$1 dir=$TASKS/$slug' dies under set -u with 'slug: unbound variable'. Hit while adding task_lock to lib.sh. Same family as the '[ cond ] && cmd' papercut from earlier today: a shell footgun that only fires under captain's own set -euo pipefail, and only on the branch nobody exercised. Every other multi-assignment local in lib.sh happens to reference $1 directly rather than an earlier variable, so none of them are affected today, but nothing stops the next one. - [x] 2026-09-09 - cap-ask's resume key could not tell one gate round from the next, so a gate resumed a finished review and restated its verdict against code it had never read. The key is sha256(profile, dir, prompt), and cap-gate sends a byte-identical review prompt every round from the same worktree with the same profile. local-env's Gate A hit its session limit at 11:51 after reaching GATE: FAIL on a missing executable bit; the round-five gate at 16:16 resumed that session, got its old conclusion restated verbatim (the capture still carried the 11:51 timestamp), and recorded FAIL against a fingerprint whose worktree had the bit set. The report file came back byte-identical to the committed one, which is what gave it away. Gate B, which had no pending resume, genuinely re-ran and passed. Fixed 2026-09-09: cap-ask folds an optional CAP_ASK_KEY into the resume key and cap-gate passes the worktree fingerprint, so a resume can only ever continue a review of the exact code that was interrupted. Any other caller whose prompt is constant across calls that mean different things must supply its own discriminator.
- [x] 2026-09-09 - `cap send` gives up when the task's pane is gone: it prints "pane 'local-env' is not live" and exits, so the message is lost and the captain is left holding work the agent should be doing. Hit on local-env, whose pane had died while the task itself was still open and mid-round; the correction meant for the agent had to be applied by hand instead. The task record still holds everything needed to bring the session back (CAP_TREE, CAP_BRANCH, CAP_PANE, CAP_MODEL, CAP_HARNESS in state/tasks/<slug>/task.env), which is how cap-spawn opens one in the first place. cap-send should detect the dead pane, relaunch the session against the same worktree with the task's own brief and status log as context, and then deliver the message, rather than making a dead pane the captain's problem. The message goes in the prompt rather than arriving as a second turn, because a freshly launched pane is already busy. It announces the restart, since a revived session has lost the conversation the original was carrying.
- [x] 2026-09-09 - cap-spawn writes the path-ownership hook to <worktree>/.claude/settings.local.json and excludes it via the repo's .git/info/exclude, but that mechanism fails open twice over. And that shared file is not owned by Captain: the entry written for aula at 16:xx was gone by 17:xx, leaving .claude/ untracked in the aula-tooling worktree where a 'git add .' would have committed Captain's hook config into the project. - [x] 2026-09-10 - `printf '%s\n' "$big" | grep -q pattern` under captain's own `set -euo pipefail` can report a real match as "not found" whenever the match isn't on the last line of a large buffer. `grep -q` exits the instant it finds a match, before `printf` finishes writing the rest into the pipe; `printf` then dies of SIGPIPE (141), and pipefail reports that 141 as the pipeline's exit status instead of grep's real 0. Found chasing a false positive in cap-check's stale-symbol scan: relq-executor-ergonomics' diff genuinely re-added `__init__` twelve times, but the 74KB diff made the match land well before the end, so `cap check` reported the method as removed-and-still-referenced. Reproduced deterministically (4/4) once isolated from `cap-check`'s real code path, and confirmed the failure disappears with a here-string instead of a pipe. `bin/cap-ask`'s session-limit check (`printf '%s' "$tail_from_prompt" | grep -qF "hit your session limit"`) has the identical shape against a buffer that can run to ~1000 lines - a genuine rejection banner occurring early in that capture could have gone undetected the same way, silently letting a truncated response pass as real. Fixed 2026-09-10: both switched to `grep ... <<<"$var"`, which has no pipe to break. `grep -rn '| grep -q' bin/` turned up three more (cap-check's own surface-map check, lib.sh's `owns_regex` check, cap-send's chunk-delivery check) but those pipe short, single-path/filename-sized strings that fit in one pipe-buffer write, so the race window in practice is far narrower; left alone rather than converting everything on spec.
- [x] 2026-09-09 - cap-ask's `herdr pane read` call (bin/cap-ask) had no `--lines` argument, so it defaulted to reading only the visible viewport (~80 lines) instead of the scrollback. - [x] 2026-09-10 - cap check's em-dash scan reads the diff, so it cannot tell our own added prose from a verbatim copy of an external file that must match byte-for-byte. classroom's .devstack/generate-config.sh carries a STRIP_LINES heredoc holding two comment lines lifted exactly from .cicat/config.php.example, em dashes included; the strip and its self-verification both match those lines literally, so "fixing" the punctuation would silently stop the strip from finding them. The scan flags them on every round, and the only way to clear it is to remember why not to. A file-level or line-level opt-out (a marker comment, or skipping heredocs whose content is asserted equal to a tracked file) would stop the check from training the captain to ignore it. Fixed 2026-09-10 by deleting the scan. The character was standing in for a judgment about sentence structure: it caught one punctuation form of a two-idea sentence, missed every sentence that does the same with a comma, and produced this false-positive class of its own. The opt-out written for it needed a marker syntax and a rule for verifying the marker's claim, which is a lot of machinery to defend a proxy nobody wanted measured. Readability already has an owner. AGENTS.md leads with plain writing, rules/comments.md carries the checklist, and cap cleanup runs a model pass over both on every task. NORTH.md says repeated deterministic checks belong in scripts and infrequent judgment belongs in a focused model pass; this was judgment in a grep.
- [ ] 2026-09-10 - `pgrep -f` is unusable for polling task processes once `cap send` has revived a session, because the revive puts the captain's entire message inside the launch prompt and the harness carries that prompt in its argv. A gate round's instructions run to several thousand characters and quote the exact commands the agent is told to run, so `pgrep -f 'mise run check'` matched the claude session itself, not the check. Hit twice in a row today on local-env: two `until ! pgrep -f ...; do sleep; done` waiters never terminated because the agent's own command line kept matching, and one had to be killed by hand. Anything that waits on a task's real work should watch the work's own output file or pid, or at least anchor the pattern to the binary (`pgrep -f '^mise '`, `pgrep -x`), never a phrase that could appear in a brief or a captain message. Worth considering whether cap-send should pass the revival text through a file or stdin instead of argv, since argv is world-readable on this box and the same message can carry findings that quote source.
- [ ] 2026-09-10 - killing cap-gate does not kill the review it launched, so the account keeps paying for an Opus session whose verdict nobody will ever record. herdr starts the reviewer in its own pane, detached from cap-gate's process tree, so when the harness's low-memory guard killed the backgrounded `cap gate local-env --full` seconds after it started, the wrapper died and the opus process (pid 1637014, pane w2:p1E) carried on reviewing for another ten minutes with nothing left to read its output, promote the report or call gate_record. Recovered by hand this time: waited on the orphan's pid, read the pane, wrote notes/classroom/local-env.gate-A.md and called gate_record with the fingerprint directly. The same shape applies to any interruption of cap-gate, Ctrl-C included, and it is worse than a wasted review because state/tasks/<slug>/gate.json still holds the previous round's verdict at a stale fingerprint, which reads exactly like a gate that was never run. cap-gate should either trap EXIT and close the pane it opened, or record enough (pane id, fingerprint, profile) that a later run can adopt an orphaned review instead of paying for it twice.
