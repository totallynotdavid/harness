- [ ] 2026-09-05 - relq: Column's dataclass-generated frozen __setattr__/__delattr__ raises a raw TypeError ('super(type, obj): obj (instance of Column) is not an instance or subtype of type (Column)') instead of dataclasses.FrozenInstanceError whenever code attempts to mutate a Column instance's attribute (e.g. users.id.foo = 1). Confirmed pre-existing: reproduces identically on cap/relq-conflict-arity (before any Python-floor work) under Python 3.15.0rc1, so it is unconditional and version-independent, not tied to the 3.13/3.14 patch-release bisection found while lowering the floor. Root cause: dataclasses' own generated frozen accessor methods close over the pre-slots-rebuild class object via the same super(cls, self) pattern that _node_value.py's NodeValue fix addresses for hand-written methods, but Column (and potentially other @dataclass(frozen=True, slots=True) classes elsewhere in relq, e.g. query.py's SelectQuery family) still ask for slots=True via the decorator and were never audited. A caller catching AttributeError/FrozenInstanceError to detect a mutation attempt gets an uncaught TypeError instead. Fix would mean applying the same hand-declared-__slots__-instead-of-slots=True treatment (and getstate/setstate correctness) across every frozen+slotted dataclass in relq, verified the same way NodeValue was - real, separate task, not part of lowering the Python floor. See notes/relq/relq-conflict-where.md for the floor task's own investigation.

- [ ] 2026-09-05 - rqueue: Worker.run() doesn't actually return promptly on shutdown when a handler used asyncio.to_thread for long CPU-bound work. bounded_default_executor's cleanup (executor.py) calls ThreadPoolExecutor.shutdown(wait=True) synchronously on the event loop when the Worker's _runtime() context manager exits -- this blocks until every submitted thread genuinely finishes, even though _shutdown_inflight() already cancelled the coroutine and handed the lease back within shutdown_timeout. Confirmed directly: a 3s blocking thread, cancelled at ~0.1s, still blocks the 'with bounded_default_executor(...)' block's exit for the full 3s. For a tens-of-minutes handler this means the worker process doesn't actually exit on SIGTERM until the in-flight work finishes on its own, even though the lease was already correctly handed back to another worker -- two workers can then be alive concurrently past the point rqueue's own shutdown sequence implies is safe. Likely fix: shut the executor down off the loop thread (asyncio.to_thread(executor.shutdown, wait=True)) or with wait=False plus a documented note that threads may outlive the executor. Found via picv-2025's cap/picv-asyncpg-rqueue-v2 gate review (round 5); out of scope for that task since the defect is in rqueue itself.
